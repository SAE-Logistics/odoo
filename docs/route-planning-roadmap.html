Run Sequencing Plan

How to get driver manifests into the order the run is actually driven — inside Odoo, before the PDF prints.

12 August 2026 Odoo 18 · Community Findings verified on staging

The problem is the model, not the screen

A run does not exist as a record. driver_id and fleet_id are stamped onto individual transport legs, and a run is an ad-hoc multi-select made at print time. There is no object to hang an order on, no object to hang a status on, and nothing to reprint from.

That is why re-ordering has nowhere to live. A sequence field alone papers over it; a record for the run itself is what actually fixes it.

Already shipped — 12 Aug 2026

The Excel export is live. Tick the legs, then Actions → Driver Manifest (Excel): one sheet per driver, same nine columns as the PDF, landscape fit-to-width with the header row repeated, autofilter and frozen header. Rows can be re-ordered and printed from Excel.

It is a workaround, not the destination — the new order does not come back into Odoo. Everything below is about closing that gap.

What the ground looks like

Checked directly against the staging instance, because two of these rule out the obvious approaches.

Edition Community. No web_gantt, web_map or web_enterprise installed; planning is uninstallable. No Gantt dispatch board, no map view, no Planning app.
Available today fleet installed. base_geolocalize present but uninstalled — there if route optimisation is ever wanted.
Data hygiene Of 11 internal legs, 9 have no from_date and 6 have no driver. Grouping a run by driver and date needs that date populated.
Ordering UI options List drag-handle, kanban drag, or custom OWL. Anything richer is built by hand on Community.

Four stages, each gating the next

The order matters: every stage produces the knowledge the following one needs. Stage 0 is a prerequisite, not an improvement — the rest sits on top of it.

0

Populate from_date on internal legs

Hours

Backfill the existing legs and make the field required, or default it, on the paths that create them. Worth doing on its own merits, and every stage below groups runs by driver and date.

Gate: without a reliable date, runs cannot be formed automatically and the migration in Stage 2 has nothing to group on.
1

A manifest_sequence field on the leg

Shipped — 28 Aug 2026

Done. manifest_sequence integer with the handle widget as the first column of the Transport Legs list (sae_driver_manifest/views/sale_transport_leg_views.xml), list default_order set to it. The PDF and the Excel export both lead their sort with it, falling back to the pickup-postcode order for an untouched run. Filter the list to one driver, drag rows into order, print. Stage 0 turned out not to be a prerequisite — filter by driver, not date.

Known weakness: the sequence is global across all legs, so it only reads correctly when the list is filtered to one driver, and two dispatchers working different runs interleave their numbers. Fine as an interim. Not the destination.
2

A sae_transport_run module — the real fix

1–2 weeks

A sae.transport.run record: reference, date, driver, vehicle, state (draft → released → in progress → done), legs as a one2many with a per-run sequence, plus computed totals for drops, weight and packages.

  • Ordering lives on the run and is scoped to it. A drag handle inside the run form is standard Odoo — no custom JavaScript.
  • Driver and vehicle move up to the run, but driver_id stays writable on the leg: setting it moves the leg into that driver's run for its date, creating the run if needed. That preserves the bulk-edit habit the list view was built around, and doubles as the migration — existing legs group by driver and date into runs.
  • The manifest and delivery notes print from the run, one run to a page, with the current leg-list binding kept for ad-hoc prints.
  • Run states give reprints, an audit trail, and a natural lock: a released run stops re-ordering.
  • Right moment to collapse the duplicated row logic the Excel export introduced — the QWeb template and the Python builder derive the same nine columns twice today.
Scope boundary: runs cover internal fleet legs only. Carrier-booked legs stay with the booking framework — a DPD consignment is not part of a driver's run sheet.
3

A dispatch board

≈ 1 week

Start with no custom JavaScript at all: a leg kanban grouped by run (drag a card between columns to assign it), a calendar view by date for the week, and the drag handle inside the run for sequencing.

Deliberately deferred: a two-pane board — unassigned legs on the left, runs on the right — is genuinely custom work on Community. Run the simple version for a month first, then decide with real usage evidence.
4

Route optimisation — optional

1–2 weeks

Geocode the leg addresses, then nearest-neighbour plus 2-opt to propose a sequence the dispatcher accepts or overrides, with distance and duration estimates and a capacity check against the vehicle. Self-hosted OSRM or ORS for the distance matrix.

Worth structuring as a pluggable provider registry — the same shape as TransportBookingAdapter in transport_booking_core — so a routing provider is swappable the way a carrier already is.

Effort at a glance

Stage Effort Depends on What it unlocks
0 · Date backfill Hours — Runs can be formed and migrated
1 · Sequence field Shipped — Re-order in Odoo, print ordered PDF
2 · Run module 1–2 weeks Stages 0–1 in live use Scoped ordering, states, reprints, audit
3 · Dispatch board 1 week Stage 2 Assign and sequence visually
4 · Optimisation 1–2 weeks Stage 2 Proposed order, distance, capacity checks

Recommended sequencing: fix the dates, ship Stage 1, then run it live for a few weeks to learn how SAE actually sequences a day before committing to Stage 2. Stages 3 and 4 only once runs exist as records.
